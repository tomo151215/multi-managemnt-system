# Git開発ルールガイドライン

本プロジェクトにおけるGit運用およびチーム開発のガイドラインです。  
開発の破綻を防ぎ、スムーズなコラボレーションを行うために全員で本ルールを遵守してください。

---

## 開発環境の前提

- **エディタ**: Visual Studio Code (VSCode)
- **ターミナル**: Git Bash（VSCode統合ターミナル）

---

## 1. ブランチ戦略（GitHub Flowベース）

本プロジェクトでは **GitHub Flow** を採用します。

### GitHub Flow とは？

GitHub Flow は、GitHub が推奨するシンプルで軽量な開発フローです。

- **特徴**: ブランチは「常にリリース可能な 「`main` ブランチ」と「トピックブランチ（作業用ブランチ）」の2つのみで運用します。

### ブランチの種類と役割

- **`main` ブランチ**
    - 単体で常に動く安定状態（プロダクションレベル）を保ちます。
    - **`main` への直接コミット・プッシュは厳禁**です。
- **トピックブランチ（`feature/*`）**
    - 各タスクの作業を行うためのブランチです。`main` から作成し、作業完了後にPR（プルリクエスト）を出します。

---

## 2. ブランチ命名ルール

ブランチ名は **`feature/内容の概要`** とします（`内容の概要`は**半角英数字**、区切りはハイフン `-`）。  
※`git switch -c feature/ユーザー認証機能` のようにブランチ名に日本語を使うと、ターミナル環境やOSの文字コード（UTF-8, Shift-JIS, CP932等）の違いによって、文字化けしたり、タブ補完がうまく効かなくなったりするリスクがあるため日本語を使うのはNGです。

| プレフィックス | 用途               | 例                   |
| :------------- | :----------------- | :------------------- |
| `feature/`     | 新機能の追加・変更 | `feature/user-login` |

---

## 3. コミットメッセージのルール

コミットメッセージは下記のように記述してください。  
`要約メッセージ`は変更内容が明確に伝わるようにします。

```
プレフィックス：要約メッセージ
```

### プレフィックス一覧

| プレフィックス | 用途                                         | 使用例                                                          |
| :------------- | :------------------------------------------- | :-------------------------------------------------------------- |
| `add`          | 新しいファイルや機能の追加                   | `add: ログイン画面のバリデーション処理を追加`                   |
| `update`       | 既存の機能やファイルを変更・更新する         | `update: ユーザー一覧の取得APIのエンドポイントを変更`           |
| `remove`       | 不要なファイルや機能を削除する               | `remove: 使われなくなった古いデバッグ用ログ出力を削除`          |
| `fix`          | バグや不具合を修正する                       | `fix: ログイン時にNullPointerExceptionが発生する不具合を修正`   |
| `hotfix`       | 重大なバグや不具合を修正する                 | `hotfix: 本番環境で決済処理が失敗する緊急バグを修正正`          |
| `clean`        | コードを修正し、改善する　(リファクタリング) | `clean: ユーザー認証処理のリファクタリングと不要なコードの削除` |
| `docs`         | バグや不具合を修正する                       | `docs: READMEに環境構築の手順とAPI仕様を追加`                   |

### 良い例

- `add: ユーザーログイン画面のレイアウト作成`
- `fix: フォーム送信時のバリデーションエラーを修正`

### 悪い例

- 曖昧：`fix: バグ修正`
- 詳細すぎる：`add: ユーザーがログインフォームに入力した情報を検証して...`
- 複数の変更：`add: ログイン機能追加とバグ修正とドキュメント更新`

## 4. GitHub Flow に沿った基本操作・開発フロー

全員が共通してスムーズに開発を進められるよう、以下の6ステップを基本手順とします。  
※ コマンド操作（Git Bash）で行う場合の標準手順です。

### Step 1: 最新の `main` からブランチを作成する

作業を始める前に、必ずリモートの最新 `main` を取り込み、そこから作業ブランチを作成します。

```bash
# 1. main ブランチに移動
git switch main

# 2. リモートの最新情報を取得
git pull origin main

# 3. 作業用ブランチを作成して移動
git switch -c feature/login-form
```

- **チェックポイント:** `git branch` を実行し、作成したブランチ名の先頭に `*` がついていることを確認します。

---

### Step 2: コード変更とローカルでのコミット　

タスクを実装し、意味のある単位でこまめにコミットします。（テスト時に確実に動く状態）

```bash
# 変更ファイルを確認
git status

# コミット対象に追加
git add .

# ルールに従ったコミットメッセージでコミット
git commit -m "add: ログインフォームの画面レイアウト作成"
```

---

### Step 3: リモートリポジトリへのPushとPR（プルリクエスト）作成

実装が完了したら、リモートにPushしてPRを作成します。

```bash
# 作業ブランチをリモートへPush
git push origin feature/login-form
```

#### PR作成手順

1.  GitHubのリポジトリページを開きます。
2.  「Compare & pull request」ボタンを押してPR作成画面に進みます。
    ![error](https://tamotech.blog/wp-content/uploads/2025/05/PR%E3%81%AE%E4%BD%9C%E6%88%90%E5%A0%B4%E6%89%80-768x297.jpg)

    ※ここにハイライトされるのは、`直近のpushに対してのみ`です。しばらく時間が経つとここには表示されなくなるため「Pull requests」タブからPRを作りましょう。

3.  概要（実装内容・動作確認方法など）を入力後、画面下の 「Create pull request」 ボタンをクリックしてPRを作成（Open）します。
    ![error](https://tamotech.blog/wp-content/uploads/2025/05/PR%E4%BD%9C%E6%88%90%E7%94%BB%E9%9D%A2%E3%81%AE%E8%A7%A3%E8%AA%AC-1024x574.jpg)
    `baseブランチ`：変更を取り込みたい先（例：main）。通常は本番用（main）になることが多いです。  
    `compareブランチ`：変更を提案する側のブランチ（例：feature/login）。自分が作業していたブランチを指定します。  
    `タイトル・本文`：このPRで何を変更したのか、なぜその変更が必要なのかを記載します。読み手が理解しやすいよう簡潔にまとめましょう。  
    `レビュアーのアサイン設定`：誰にレビューしてほしいかを指定します。レビュー対象者に通知され、確認・コメント・承認が行われます。

#### PR作成の例

1.タイトル（Add a title）

```bash
add: ユーザー認証機能およびログイン画面の実装
```

2.本文（Add a description）

```bash
## 概要
ユーザーがIDとパスワードを入力してログインできるようにするための機能を実装しました。

## 変更内容
- ログイン処理を行う `LoginServlet.java` の追加
- ユーザー認証ロジック (`LoginService`) の実装
- ログイン画面のレイアウト（`login.jsp`）の作成
```

---

### Step 4: コードレビューとフィードバック対応

チームメンバーにレビューを依頼（Assign / Reviewers 設定）します。

- **修正が必要な場合:**
  ローカルでコードを修正し、再度コミットしてPushします。PRには自動的に新しいコミットが追加されます。
    ```bash
    git add .
    git commit -m "fix: レビュー指摘事項のスタイル調整"
    git push origin feature/login-form
    ```

---

### Step 5: 最新 `main` の取り込み（競合防止）

開発中に他のメンバーが `main` にマージを行った場合は、自分のブランチにも最新 `main` を取り込んでおきます。  
**※下記コマンドは自分の作業ブランチ内で実行する**

```bash
git fetch origin
git merge origin/main
```

---

### Step 6: `main` へのマージとローカルの整理（チームリーダー ・ 責任者のみ）

レビューで **Approve（承認）** を得たら、マージを行ってブランチを整理します。

1. GitHub上で「Squash and Merge」（または「Merge pull request」）を実行します。
2. GitHub上の不要になった作業ブランチを削除します（「Delete branch」ボタン）。
3. ローカル環境も最新化して整理します。

    ```bash
    # mainに戻る
    git checkout main

    # 最新のmainを取得
    git pull origin main

    # ローカルの作業ブランチを削除
    git branch -d feature/login-form
    ```

---

## 5. プルリクエスト（PR）とレビューのルール

- **PRの粒度**: 1つのPRの大きさは自由
- **レビュー担当者（Reviewer）の指定**: チームメンバーを少なくとも1名指定します。
- **マージ条件**:
    - 最低1人以上のレビュアーからの **Approve** を取得すること。
    - CIテスト（設定されている場合）が通過していること。

---

## 6. コンフリクト（競合）が発生した場合の対処法

コンフリクト（競合）は、同じファイルの同じ行を複数人が同時に変更した際に発生します。以下の手順に従って解消してください。

### 手順1: 最新の `main` を自分のブランチに取り込む

自分の作業ブランチ（例: `feature/login-form`）にいる状態で、Git Bash で以下を実行します。

```bash
git fetch origin
git merge origin/main
```

「`CONFLICT (content): Merge conflict in ...`」という警告が出たらコンフリクトが発生しています。

---

### 手順2: VSCodeのエディタ上で競合箇所を修正する

1. VSCodeの左メニュー「ソース管理」タブ（Gitアイコン）を開きます。
2. 「コンフリクトの発生した変更」に一覧表示されているファイルをクリックします。
3. エディタ上の対象コードの上に表示されるボタンを押して変更を選択します：
    - **`Accept Current Change`（現在の変更を保持）**: 自分が書いたコードを残す
    - **`Accept Incoming Change`（取り込み側の変更を保持）**: 相手（`main`）が書いたコードを残す
    - **`Accept Both Changes`（両方の変更を保持）**: 両方のコードを順番に残す
    - ※ボタンを使わず、`<<<<<<<` や `>>>>>>>` の表示を手動で消して直接修正しても構いません。

---

### 手順3: 動作確認とマージコミットの送信

1. コンフリクト箇所を修正後、ファイルに保存（`Ctrl + S`）し、アプリが正常に動作するか確認します。
2. Git Bash で解消後の変更をコミットしてPushします。

```bash
# 修正したファイルを追加
git add .

# マージコミットを作成
git commit -m "fix: resolve merge conflicts with main"

# リモートへPushしてPRに反映
git push origin feature/login-form
```

---

## 7. トラブル時の対処法

### 間違ってmainで作業してしまった

```bash
# 1. 変更を退避（mainブランチ内で実行）
git stash

# 2. ブランチ作成して切り替え
git checkout -b feature/correct-branch

# 3. 変更を戻す（#2で作ったブランチ内で実行）
git stash pop

```

---

## 8.絶対に守ることまとめ

1. mainで直接作業しない（自分のブランチ内で作業する）
2. mainをpullせずにpushしない（コンフリクト対策）
3. 他人のブランチで強制pushしない
4. わかりやすいコミットメッセージ
5. こまめにコミット・プッシュ（実行時にエラーが出る状態のプログラム等はコミット・プッシュしない）
6. 機密情報をコミットしない

## 9. 使用コマンド早見表

日常の開発（Git Bash）でよく使うコマンド一覧です。操作に迷った際はこちらを参照してください。

| 操作・目的                                                | コマンド例                                            |
| :-------------------------------------------------------- | :---------------------------------------------------- |
| 現在のブランチ・変更状態の確認                            | `git status`                                          |

| `main` ブランチに切り替え                                 | `git switch main`                                     |
| リモートの最新情報を取得・反映                            | `git pull origin main`                                |
| 新しい作業ブランチを作成して移動                          | `git switch -c feature/xxx`                           |
| 変更したすべてのファイルをステージング                    | `git add .`                                           |
| 変更した指定ファイルをステージング                        | `git add <ファイル名>`                                |
| コミットの実行                                            | `git commit -m "feat: メッセージ"`                    |

## 1. ssh-agentの登録

### ssh-agentとは？

SSHの秘密鍵とそのパスフレーズ（暗号化を解除するパスワード）をメモリ上に一時的に保持・管理してくれるバックグラウンドプログラムです。  
`ssh-agent`を起動して秘密鍵を登録しておくことで、`git push` や `git pull` などのGit操作を実行するたびのパスフレーズ入力を省略できます。

[ssh-agentを使ってgithubへssh接続する](https://qiita.com/ggg-mzkr/items/fd32e1a6b7353ca52d3c)にアクセスし、サイトの手順に沿ってssh-agentを登録してください。

## 2. ブランチ保護ルールの設定（チームリーダーのみ）

### 1. Collaborator（コラボレーター）の権限設定

リポジトリに開発メンバーと責任者に適切な権限を割り振ります。

#### 権限（Role）の割り当て

環境（個人リポジトリかOrganizationリポジトリか）によって割り当てる権限を選択します。

- **個人アカウント（Personal Account）のリポジトリの場合:**
    - 全員の権限は自動的に一律 **`Write`（書き込み可能）** に設定されます（個人リポジトリではロールの細かい変更はできませんが、後のブランチ保護ルールでマージ制限をかけるため問題ありません）。  
      ※リポジトリの完全な管理者（`Admin`）は、リポジトリの所有者（オーナー本人）のみとなります。
- **Organization（組織）のリポジトリの場合:**
    - **開発メンバー**: **`Write`（Write / Push 権限）** を付与します（コードの読み書き・ブランチ作成・PR作成が可能になります）。
    - **責任者**: **`Write`** または **`Admin`（管理者権限）** を付与します。

---

### 2. 【リポジトリ側】`CODEOWNERS` ファイルの作成

リポジトリ内に責任者を指定する設定ファイルを作成します。

1. リポジトリの直下（または `.github/` ディレクトリ内）に **`CODEOWNERS`** という名前のファイルを作成する。
2. 以下の1行を記述し、メインブランチへコミット＆プッシュする。

```text
* @責任者アカウント1 @責任者アカウント2 @責任者アカウント3　
```

※ `@` の後ろにGitHubのユーザー名を半角スペース区切りで記述してください。

---

### 3. 【GitHub設定】ブランチ保護ルールの追加

対象のブランチに対してルールを適用し、承認のないマージや直接プッシュを禁止します。

1. GitHubで対象リポジトリを開き、**Settings** ＞ **Branches** へ移動する。
2. **Add classic branch protection rule** ボタンをクリックする。
3. **Branch name pattern** に制限したいブランチ名を入力する（例: `main` や `release`）。
4. 以下の設定項目に**チェックを入れる**:
    - [x] **Require a pull request before merging**（直接プッシュの禁止）
        - [x] **Require approvals**（必要な承認人数を `1`〜`3` 人で選択）
        - [x] **Require review from Code Owners**（責任者の承認を必須化 ※最重要）
    - [x] **Do not allow bypassing the above settings**（管理者であってもルール無視を禁止）

5. ページ最下部の **Save changes**（または **Create**）をクリックして設定を保存する。
